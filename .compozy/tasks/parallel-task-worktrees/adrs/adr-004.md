# ADR-004: Carry Parallel Mode and Explicit Task Selection as First-Class Run Inputs

## Status

Accepted

## Date

2026-05-28

## Context

The current task-run request and runtime configuration do not have first-class fields for either parallel execution mode or explicit selected task identifiers. Today, PRD task runs resolve a workflow directory and then scan for all pending task files. That behavior is insufficient for the approved product contract because `--multiple` must preserve the user’s chosen task set and the effective execution mode must be visible to the daemon and planner.

The user selected explicit selected tasks as the preferred technical model and chose first-class request fields over raw runtime overrides or artifact inference.

## Decision

Compozy will add first-class run inputs for:

- the effective multiple-task execution mode, and
- the explicitly selected task identifiers produced by `--multiple`.

These fields will cross the CLI, daemon API contract, and runtime configuration boundary directly rather than being hidden inside untyped runtime override payloads or inferred from disk at execution time.

## Alternatives Considered

### Alternative 1: Runtime overrides only

- **Description**: Encode the mode and selected tasks inside the existing raw runtime override payload.
- **Pros**: Smaller public contract change and less explicit request modeling.
- **Cons**: Weak typing, weaker validation, harder tests, and more hidden coupling between CLI and daemon.
- **Why rejected**: This feature introduces durable execution semantics, so the boundary should be explicit and validated.

### Alternative 2: Infer everything from workflow files

- **Description**: Keep scanning the workflow directory and avoid passing selected tasks through the request.
- **Pros**: Minimal request changes.
- **Cons**: Breaks the `--multiple` selection contract and makes child-run scope ambiguous.
- **Why rejected**: The daemon must know exactly which tasks were selected.

### Alternative 3: Temporary selection manifest

- **Description**: Write selected tasks to a temporary file and have the daemon read that file.
- **Pros**: Preserves explicit selection without expanding the request shape as much.
- **Cons**: Adds another artifact type, another failure mode, and more cleanup complexity.
- **Why rejected**: It introduces indirection without giving V1 enough value in return.

## Consequences

### Positive

- Makes the `--multiple` contract explicit and testable.
- Improves validation at the CLI, API, and runtime layers.
- Lets the planner distinguish between “all pending tasks” and “user-selected tasks” cleanly.
- Keeps future parallel and sequential decisions visible throughout the pipeline.

### Negative

- Requires contract and configuration changes across several layers.
- Expands compatibility surface for task-run requests.
- Forces migration of some code that currently assumes task selection is always directory-driven.

### Risks

- **Field drift across layers**: CLI, API, and runtime config could diverge; mitigate by keeping one normalized runtime representation.
- **Backwards-compatibility confusion**: older flows may still expect directory-only behavior; mitigate by preserving existing defaults when explicit selection is absent.
- **Validation gaps**: malformed selected-task lists could fail late; mitigate by validating selection early against discovered task entries.

## Implementation Notes

The TechSpec should specify field names, validation rules, defaulting behavior, and how selection is normalized before planning.
