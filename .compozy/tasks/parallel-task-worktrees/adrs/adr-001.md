# ADR-001: Bound V1 to Configurable Parallel Worktree Mode With Agent Handoff

## Status

Accepted

## Date

2026-05-28

## Context

Compozy already supports multiple task selection through `tasks run --multiple`, but execution remains queued/sequential. The executor has general concurrency primitives, but PRD task runs are ordered and write shared `.compozy/tasks/<slug>` state. The codebase has workspace snapshotting for change detection, but no git worktree lifecycle layer for creating, supervising, or cleaning isolated task workspaces.

Market research shows that Claude Code, OpenAI Codex, Cursor, and Jules already use worktrees or parallel agent sessions. Compozy's differentiator is not generic parallelism; it is the structured pipeline from PRD task breakdown to isolated implementation and safe fan-in for a solo maintainer.

The council split on V1 ambition. Most advisors warned against over-scoping into a general orchestration engine. The strongest dissent argued that isolation alone is table stakes and V1 should expose a visible handoff outcome so the feature feels like leverage, not plumbing. User review resolved the scope toward configurable parallel mode, retained worktrees, and an agent cleanup/fan-in prompt.

## Decision

V1 will add a configurable multiple-task execution mode in `config.toml`: `multiple = "sequential"` remains the default, and `multiple = "parallel"` enables isolated parallel execution for tasks selected through the existing `tasks run --multiple` flow.

In parallel mode, Compozy will create one git worktree per selected task, run each child task inside its assigned worktree, preserve the original working directory, report each child run's terminal status, keep all created worktrees after execution, and generate a provider-neutral prompt for the user's chosen agent to inspect retained worktrees and prepare cleanup or PR/MR creation.

V1 will not automatically resolve conflicts, infer task dependencies, perform unattended merges, create provider-specific PRs/MRs, automatically clean worktrees, or become a general-purpose scheduler. A task is marked finished when its child run finishes successfully in its isolated worktree.

## Alternatives Considered

### Alternative 1: Isolation-only MVP

- **Description**: Create worktrees and launch parallel task runs, but stop before any cleanup or fan-in handoff concept.
- **Pros**: Lowest implementation risk, validates worktree lifecycle first, minimizes shared-state changes.
- **Cons**: Looks like infrastructure plumbing, weakens the product promise, and may underdeliver against competing worktree-based agent products.
- **Why rejected**: A provider-neutral agent handoff prompt is a small product-shaped outcome that preserves scope discipline without adding provider-specific PR/MR automation.

### Alternative 2: Full parallel orchestration engine

- **Description**: Add dependency-aware scheduling, automatic merge/conflict handling, retries, cleanup policy, provider integrations, and run-board management in V1.
- **Pros**: Strongest long-term product story and highest perceived leverage.
- **Cons**: Expands V1 into scheduler, state reconciliation, and merge-policy work before the worktree substrate exists.
- **Why rejected**: Too much architectural and trust risk for V1; it could turn a solo-maintainer workflow into a distributed coordination system inside the CLI.

### Alternative 3: Reuse review remediation batching model

- **Description**: Adapt the existing review-fix batching/concurrency model for task execution.
- **Pros**: Reuses familiar concurrency UX and existing batch concepts.
- **Cons**: Review issues and PRD tasks have different state, dependency, and completion semantics.
- **Why rejected**: It risks confusing two workflows and does not solve worktree isolation or task artifact race conditions directly.

## Consequences

### Positive

- Gives the feature a clear product outcome: safe isolated execution plus a provider-neutral agent handoff prompt.
- Protects the main worktree while allowing a solo maintainer to explore parallel task implementation.
- Creates a foundation for future dependency-aware scheduling and richer reconciliation without committing to them in V1.
- Preserves provider neutrality by handing off cleanup and PR/MR preparation to the user's chosen agent.

### Negative

- Requires more than a pure worktree launcher, including status aggregation and agent handoff prompt UX.
- May delay the first ship compared with isolation-only scope.
- Leaves users to handle actual conflict resolution, cleanup, and PR/MR creation manually or through their chosen agent in V1.
- Retaining every worktree can increase local disk usage.

### Risks

- **Shared task state races**: mitigate by defining ownership rules for task artifact writes and avoiding concurrent writes to the same files in V1.
- **Overpromised fan-in**: mitigate by documenting the handoff prompt as guidance for the user's agent, not automatic merge success.
- **Cleanup/data-loss risk**: mitigate by keeping all created worktrees and making cleanup an intentional follow-up action.
- **Config ambiguity**: mitigate by documenting `multiple = "sequential"` and `multiple = "parallel"` examples clearly.

## Implementation Notes

Implementation details belong in the future TechSpec. The idea and PRD should specify user-visible behavior and scope boundaries only.
