# ADR-005: Defer Source Workflow Mutation and Persist the Handoff Prompt as a Run Artifact

## Status

Accepted

## Date

2026-05-28

## Context

The approved PRD requires the source workspace to remain untouched during child execution, but current PRD task success handling marks tasks completed by rewriting workflow markdown in the task directory. The approved PRD also requires a copy-paste-ready handoff prompt for the user’s chosen LLM or coding agent.

The user selected three related technical constraints:

- Source-workspace task updates should be deferred rather than synced back automatically during child execution.
- The handoff prompt should be durable in run artifacts.
- The prompt should also be visible directly in final output rather than hidden only behind a file path.

## Decision

Child runs in parallel mode will not mutate workflow task files in the source workspace.

Instead, the parent run will persist a durable handoff artifact set under the run directory, including the copy-paste prompt and the child outcome summary. The final run summary will both point to the artifact location and echo the prompt text in operator-visible output.

Source-workflow task completion or reconciliation will happen later, from the source workspace, during an explicit fan-in or cleanup step rather than during child execution.

## Alternatives Considered

### Alternative 1: Automatically sync task-file updates back from child worktrees

- **Description**: Let child worktrees rewrite copied task files and automatically reconcile those changes into the source workflow at the end.
- **Pros**: Keeps workflow task status immediately current.
- **Cons**: Violates the trust requirement around untouched source state during child execution and creates hidden reconciliation behavior.
- **Why rejected**: V1 must keep source mutation intentional and visible.

### Alternative 2: Store completion only in run metadata

- **Description**: Never update task files and rely exclusively on run metadata for completion semantics.
- **Pros**: Simplest way to avoid source mutation during child execution.
- **Cons**: Splits task truth across two models and weakens the existing task-file-driven workflow.
- **Why rejected**: The source workflow still needs a clear eventual reconciliation path.

### Alternative 3: Write the prompt into the workflow artifact directory

- **Description**: Persist the handoff prompt inside `.compozy/tasks/<slug>/`.
- **Pros**: Easy to discover next to the workflow.
- **Cons**: Mutates source workflow artifacts during the parallel run and blurs the line between durable workflow state and one-run handoff output.
- **Why rejected**: Run artifacts are the cleaner ownership boundary for per-run output.

## Consequences

### Positive

- Preserves the strongest trust guarantee in the PRD: no source-workspace mutation during child execution.
- Gives the user both a durable artifact and immediate copy-paste output for the handoff prompt.
- Keeps per-run output scoped to run artifacts instead of mixing it into long-lived workflow files.
- Makes fan-in an explicit, reviewable step.

### Negative

- Introduces a two-phase completion story: child execution first, source workflow reconciliation later.
- Requires clear UX so users understand that a successful child run is not yet the same thing as final workflow reconciliation.
- Adds a new parent-run responsibility for prompt generation and artifact persistence.

### Risks

- **State ambiguity**: users may misread successful child runs as fully completed workflow tasks; mitigate by using distinct terminology in summaries and handoff output.
- **Prompt discoverability**: users may miss the durable artifact if only a path is shown; mitigate by also echoing the prompt text in the final summary.
- **Artifact sprawl**: run directories can accumulate large handoff outputs over time; mitigate by keeping the prompt compact and tied to existing run retention behavior.

## Implementation Notes

The TechSpec should define the run-artifact file layout for handoff output, the terminal summary contract, and the explicit fan-in step that applies source-workflow task updates later.
