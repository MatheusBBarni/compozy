# ADR-002: Position V1 as a Safe Review Lane for Parallel Task Worktrees

## Status

Accepted

## Date

2026-05-28

## Context

The existing idea for `parallel-task-worktrees` already scopes V1 around isolated parallel execution and source workspace protection. During PRD brainstorming, the remaining product question was how the feature should be framed for the first release.

Research reinforced two forces. First, developer adoption of AI coding tools is high, but trust remains fragile because output is often "almost right" and still needs human review. Second, competitive workflows are converging on isolated workspaces or git worktrees for parallel agent sessions, which means isolation alone is unlikely to feel differentiated.

User clarification established five product priorities for V1:

- Review quality matters more than raw concurrency.
- The primary user is a solo maintainer.
- A successful run should end in PR-ready preparation, not only status output.
- The least acceptable risk is any change to the source workspace during child execution.
- The business success signal is higher throughput, provided trust is preserved.

The decision therefore needed to balance three goals: preserve trust, increase throughput, and give the user a concrete next step toward review.

## Decision

V1 will be positioned as a **safe review lane** for parallel task execution.

The product promise is: a solo maintainer can run selected tasks in parallel without touching the source workspace, receive isolated outputs for each task, and finish with a clear package for turning results into reviewable branches or pull-request work.

This direction keeps trust and reviewability at the center while still making throughput the top business outcome. It avoids positioning V1 as either bare infrastructure or an over-automated release system.

## Alternatives Considered

### Alternative 1: Minimal isolation lane

- **Description**: Offer safe parallel execution and status visibility, but stop short of PR-oriented handoff or packaging.
- **Pros**: Lowest scope, easiest story to ship, and strongest focus on workspace safety.
- **Cons**: Weakens the perceived product value, leaves too much post-run work undefined, and undershoots the user's desire for PR-ready preparation.
- **Why rejected**: V1 needs to feel like a product step, not just protected plumbing.

### Alternative 2: Managed release lane

- **Description**: Extend the feature toward a more opinionated downstream workflow centered on stronger release or review packaging.
- **Pros**: More differentiated story and clearer end-to-end value if it works well.
- **Cons**: Expands V1 surface area, increases expectations around downstream workflow support, and risks overcommitting before trust is earned.
- **Why rejected**: The first release should prove safe parallel review value before broadening into a larger release workflow.

## Consequences

### Positive

- Aligns the feature with the strongest user concern: safe reviewable output instead of uncontrolled agent speed.
- Preserves the trust-first character already visible in the product's task execution UX.
- Gives V1 a clear user-visible outcome beyond raw isolation.
- Supports the chosen business success signal of higher throughput without promising unattended completion.

### Negative

- Requires the PRD and future TechSpec to define a better post-run handoff experience than a status-only MVP would require.
- Leaves some downstream review and merge effort with the user.
- May look less ambitious than a broader release-management story.

### Risks

- **Value ambiguity**: users may still see the feature as worktree plumbing unless the review handoff is explicit and easy to act on.
- **Expectation mismatch**: PR-ready preparation could be misread as automatic merge or release handling unless the scope is described clearly.
- **Scope creep**: pressure may arise to add release automation into V1; mitigate by keeping the promise centered on safe review preparation.

## Implementation Notes

Implementation details belong in the TechSpec. The PRD should stay focused on user capabilities, business outcomes, and scope boundaries.
