# ADR-003: Orchestrate Parallel `--multiple` Runs as Parent and Child Runs

## Status

Accepted

## Date

2026-05-28

## Context

The approved PRD positions V1 as an opt-in parallel mode for the existing multi-task workflow. Codebase exploration shows that PRD task execution is currently serialized inside the executor, even though the executor supports concurrency in other modes. It also shows that the daemon already has a parent/child orchestration pattern in review-watch, including child launch, wait, validation, and summary flow.

The user clarified two technical constraints for V1:

- The feature must continue to use the `--multiple` task selection surface.
- Each selected task should become its own parallel execution tab only when the task run mode in `config.toml` is `parallel`.

This creates a design choice between forcing parallelism into the existing single-run executor path or using the daemon as a coordinator for isolated child runs.

## Decision

When `--multiple` is used and the effective task run mode is `parallel`, Compozy will create one parent run that coordinates one child run per selected task.

Each child run will execute in its own isolated worktree and map to its own visible execution lane or tab. The parent run will own task fan-out, child run tracking, terminal aggregation, and end-of-run handoff output. When the effective mode is `sequential`, the current ordered execution path remains in place.

## Alternatives Considered

### Alternative 1: Executor-level parallel jobs inside one run

- **Description**: Keep a single PRD task run and make the executor run PRD task jobs concurrently.
- **Pros**: Smaller surface change in the run model and no new parent/child relationship.
- **Cons**: Conflicts with the current ordered PRD semantics, shared workspace assumptions, and task completion hooks that mutate one workflow directory.
- **Why rejected**: It pushes isolation and state coordination into the executor, which is the wrong layer for worktree-based child execution.

### Alternative 2: Extension-bridge-driven child orchestration

- **Description**: Use the extension bridge as the primary runtime abstraction for child task runs.
- **Pros**: Reuses an existing detached child-run launch mechanism.
- **Cons**: The bridge currently enforces the same workspace root, which conflicts with isolated worktrees for child runs.
- **Why rejected**: It adds avoidable friction for V1 and does not fit the current worktree isolation requirement cleanly.

## Consequences

### Positive

- Reuses an existing daemon orchestration pattern instead of overloading executor semantics.
- Maps naturally to the user’s desired mental model of one selected task per parallel tab.
- Makes child-run status, retries, and final aggregation explicit.
- Preserves the current sequential path when the effective mode remains `sequential`.

### Negative

- Adds parent/child run coordination complexity for PRD task runs.
- Requires new logic for child-run visibility, result aggregation, and failure handling.
- Increases the amount of run metadata that must stay coherent across coordinator and child runs.

### Risks

- **Child-run sprawl**: too many selected tasks could create noisy UI and operator overload; mitigate by keeping `--multiple` selection explicit.
- **Status drift**: parent summary could disagree with child outcomes unless aggregation rules are strict; mitigate by deriving parent state from terminal child states only.
- **Partial failure ambiguity**: some tabs may succeed while others fail; mitigate by making per-child terminal outcomes first-class in the final handoff.

## Implementation Notes

The TechSpec should define parent/child lifecycle, status aggregation rules, and how isolated worktrees map to child run metadata and terminal presentation.
